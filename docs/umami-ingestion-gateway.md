# Umami 采集网关方案

## 目的

当大量小程序设备同时上报时，采集网关位于客户端与 Umami 之间，负责接收、校验、削峰和受控转发。它解决的是短时突发、恶意流量和 Umami/PostgreSQL 写入保护；它不是另一套统计系统，也不改变 Umami 的事件、访客或跳出率口径。

```text
小程序 SDK
  └─ POST /collect/v1/batch（HTTPS）
       └─ 采集网关：鉴权、校验、限流、持久队列
            └─ worker：小批量 POST Umami /api/batch
                 └─ Umami → PostgreSQL
```

日常低流量时，小程序可继续直连 Umami；启用网关后，仅将 SDK 的 `endpoint` 改为网关地址。客户端上报体保持 Umami 协议不变，网关不增加页面访问或“退出”事件。

## 接口契约

### 客户端 → 网关

- 地址：`POST https://analytics.example.com/collect/v1/batch`
- 请求体：Umami 事件数组；数组中每项保持 `{ type: 'event', payload: {...} }`。
- 建议上限：每批最多 10 条（与当前 SDK 一致）、整个 JSON 不超过 64 KiB。
- 成功：网关已将事件写入可靠队列时返回 `202 Accepted` 和 `{ accepted, rejected }`。这不表示 Umami 已落库。
- 参数或鉴权错误：`400` / `401` / `403`，客户端不重试。
- 限流或容量不足：`429` / `503`，客户端按指数退避和随机抖动重试。

网关也可接受单条 `POST /collect/v1/send`，但应在内部统一转换为一条批次；不要让客户端因接口变化产生两套统计逻辑。

## 网关职责

1. 仅允许预先配置的 `websiteId`、`hostname`、事件名和属性白名单；再次限制字符串长度、对象深度、批量数量和请求体大小。
2. 拒绝手机号、OpenID、UnionID、Token、完整搜索词、聊天正文等个人或业务敏感数据。网关日志只记录请求 ID、状态、数量、耗时和错误类别，不打印载荷。
3. 以网关实际连接 IP 做限流；不能信任客户端自填的 `X-Forwarded-For`。按“IP + websiteId”设置令牌桶，并设置全局并发、队列深度和请求体上限。
4. 仅使用 HTTPS；将 Umami 与数据库放在私有网络，禁止公网直接访问内部转发端口。
5. 将请求写入 Redis Streams、NATS JetStream、Kafka 等**可持久化**队列后才返回 `202`。纯内存队列在网关重启时会丢失数据，不能用于高峰削峰。

`/api/send` 本身不需要认证，因此公网网关仍可能被伪造流量攻击。推荐在网关增加短期采集令牌：小程序先通过自身业务登录或匿名注册向业务后端换取短期 token，网关验签后才入队。不要把小程序 `AppSecret` 或可长期复用的私钥放进客户端。

## 保留 Umami 访客口径

Umami 默认会用来源 IP、User-Agent 等信息生成匿名会话。若所有事件由网关转发，必须：

- 网关将**自己观测到的**客户端 IP 写入仅供内部链路使用的 `X-Forwarded-For`；
- 原样转发客户端 `User-Agent`；
- 在 Umami 的反向代理/可信代理配置中，仅信任网关来源的转发头；
- 禁止公网客户端直连 Umami 或伪造该转发头。

否则 Umami 会把所有流量看作网关 IP，导致 UV、访问和跳出率严重失真。网关不应把 OpenID、手机号或业务用户 ID 填入 Umami `payload.id`；若未来确需 distinct ID，须单独完成隐私评审和产品规则设计。

## Worker 转发与失败策略

- 一个 worker 每次取小批量（例如 20–100 条；以压测结果定值），调用 Umami `POST /api/batch`。该接口可减少 HTTP 往返，但 Umami 仍会逐项处理，因此不能无限增大批次。
- 仅在网络错误、超时、`429` 和 `5xx` 时重试；采用指数退避加随机抖动，并遵守服务端 `Retry-After`（如果提供）。
- `400`、`401`、`403` 等不可恢复错误送入死信队列（DLQ），记录脱敏原因，不无限重放。
- `/api/batch` 的响应中如果只报告部分失败，确认成功项目后仅重试失败索引；避免整批重发造成重复统计。
- 每条消息加网关生成的 `requestId` 用于追踪。Umami 采集协议不承诺端到端严格去重，因此指标允许少量“响应丢失后重试”造成的重复。

## 容量保护和监控

网关应导出并告警以下指标：

| 指标 | 告警含义 |
| --- | --- |
| 接收 QPS、`202`/`4xx`/`429`/`5xx` 比例 | 流量增长、协议错误或滥用 |
| 队列深度、最老消息年龄、DLQ 数量 | 下游 Umami/数据库处理不足 |
| worker 批次大小、转发耗时、重试次数 | 批处理效率与下游延迟 |
| Umami `/api/batch` 状态码、部分失败数 | 兼容性与数据质量 |
| PostgreSQL CPU、IOPS、连接数、慢查询 | 真正的写入瓶颈 |

当队列接近上限时，优先返回 `429` 或丢弃经产品确认的低价值重复事件；不要丢弃已确认的关键页面访问而不记录指标。客户端已有 50 条有界队列，因此网关的反压不会导致无限内存占用。

## 上线步骤

1. 以压测流量验证网关的校验、限流、队列和 worker；分别模拟 Umami 正常、慢响应、`5xx`、重启与 PostgreSQL 慢写入。
2. 对照直连与网关两组测试设备，核对页面访问、事件、UV、访问数和跳出率；特别检查转发后的 IP 与 User-Agent 口径。
3. 先让一个 `tag: test-audience` 小流量受众切换至网关，观察队列年龄、错误率和 Umami 数据一致性。
4. 灰度扩大流量；保留将 SDK endpoint 切回直连或禁用统计的配置开关。
5. 稳定后关闭 Umami 公网采集入口，只允许网关所在网络访问。

Umami 的 `/api/batch` 协议及其部分失败返回以目标部署版本实测为准。当前联调实例已用空数组验证 `/api/batch` 返回 `200` 与 `processed: 0`，但上线前仍须用脱敏测试事件验证完整转发链路。

## 与当前 SDK 的对应关系

当前 SDK 已具备 10 条/1.5 秒小批量、50 条有界队列、批量接口回退，以及带抖动的有限重试。接入网关时建议：

```js
umami: {
  endpoint: 'https://analytics.example.com/collect/v1/send',
  batchSize: 10,
  batchDelay: 1500,
}
```

网关适配完成前，不要把生产流量切到该示例地址。
